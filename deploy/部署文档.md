# semgravio-admin 部署文档（单机 Docker · 共享 infra 接入形态）

> 口径：一台已由 aiplatform 部署单元起好共享 infra（`semgravio-pg` / `semgravio-redis` /
> `webnet`）的服务器，从零到 admin 可用。本文档是**唯一部署正本**（#118 收口）：首装、
> 日常发布、服务端运维、备份恢复、secret 同步、破窗账号首登改密、分层验收与 admin-web
> 反代交接全部在此；`docs/deploy/{first-install,release}.md` 已退役为指向本档的跳转页。
>
> 依赖前提：开发机（Windows Git Bash / Mac）有本仓完整 checkout，且 cartisan-boot
> SNAPSHOT 制品在开发机 `~/.m2`（见 §1.3）——jar 只能在开发机构建，服务器无需 Java/Maven。

## 0. 交付结论（admin-web 对接，先读这个）

- **反向代理目标固定为 `http://semgravio-admin:8081`**，健康检查路径
  **`GET /actuator/health`**（期望 `{"status":"UP"}`）。
- 该地址**只在共享 `webnet` 内解析**：admin-web 的 nginx 以容器身份加入 `webnet` 反代；
  应用不映射宿主端口，宿主 8081 不是公开访问面。
- 本应用**不提供 nginx**、不做域名/DNS/证书/80/443，不管理共享 PG、Redis、nginx 生命周期。
- 容器名 = Docker DNS 名 = 镜像名 = Compose 项目名 = `semgravio-admin`。

## 1. 前置条件

### 1.1 服务器侧

- 共享 infra 已起栈且健康：`semgravio-pg`、`semgravio-redis` healthy，`webnet` 存在
  （infra 归 aiplatform 部署单元的 `deploy/infra/` 独立管理；admin 只是接入方）。
- Docker 与 Compose v2 插件可用。
- 建库建号命令在 infra 目录执行（§2.2），其余命令在应用目录执行。

### 1.2 开发机侧

- Git Bash（Windows）或 zsh/bash（Mac）；`mvn`、`docker`（本地黑盒排练用）。
- SSH 免密已配置（BatchMode）：私钥能登录 `SERVER_USER@SERVER_HOST`。

### 1.3 cartisan-boot SNAPSHOT 制品准备

框架父 POM 只在开发机本地仓库，未发布远端。新机器或 `~/.m2` 清空后，先在 cartisan-boot
仓执行一次：

```bash
cd <cartisan-boot 仓路径>
mvn install -DskipTests -q
```

发布/打包脚本不自动修改兄弟仓库——`mvn` 找不到 SNAPSHOT 会构建失败并给出明确错误，
按上面补齐后重跑。

## 2. 首装

### 2.1 准备应用目录与环境配置

首装第一步先把发布包落到服务器（一键发布的解包动作也依赖该目录已存在）：

```bash
# 开发机仓库根：打包并上传
deploy/build-bundle.sh
scp dist/semgravio-admin-deploy-*.tar.gz <user>@<host>:

# 服务器上（路径自定，与 aiplatform 部署单元平级即可）：解包并准备真实环境文件
mkdir -p ~/semgravio-admin
tar -xzf ~/semgravio-admin-deploy-*.tar.gz --strip-components=1 -C ~/semgravio-admin
cd ~/semgravio-admin
cp deploy/env.server.example .env.production
chmod 600 .env.production
```

### 2.2 建库建号（infra 官方 helper，唯一合法通道）

应用只拿**分片凭据**：PG 超管密码不出 infra，本仓不复制建库 SQL，发布脚本不自动建库、
不迁移旧数据。

```bash
cd <infra 目录>/deploy/infra/
DB_PASSWORD=$(openssl rand -hex 16) ./ensure-db-user.sh semgravio_admin
```

输出即凭据分片（幂等：重复执行须带同一个 `DB_PASSWORD`，换新值即对齐改密）：

```
DB_HOST=semgravio-pg
DB_PORT=5432
DB_NAME=semgravio_admin
DB_USER=semgravio_admin
DB_PASSWORD=...
```

把分片抄入 `~/semgravio-admin/.env.production` 的 PG 三项。
不手工 `CREATE DATABASE`——权限边界（低权限角色、CONNECT 收回）由 helper 统一重放。

### 2.3 填写其余环境配置

`.env.production` 全量口径见 `deploy/env.server.example` 注释：

| 变量 | 来源 |
|---|---|
| `SPRING_DATASOURCE_URL/USERNAME/PASSWORD` | §2.2 helper 分片（库=角色=`semgravio_admin`，host=`semgravio-pg`） |
| `REDIS_HOST` / `REDIS_PORT` | `semgravio-redis` / `6379`（共享 infra 契约） |
| `REDIS_PASSWORD` | infra 运维按 `deploy/infra/.env` 正本下发的分片（与正本 `REDIS_PASSWORD` 同值） |
| `ADMIN_API_SECRET` | §3（app-registry 中 admin-console 的 apiSecret） |
| 四个下游地址 | 模板默认值即 webnet 容器名直连，特殊拓扑才覆盖 |

### 2.4 首次发布

日常发布与首装是同一条命令（首装时远端还没有旧容器，重建即首启）：

```bash
# 开发机仓库根（连接参数见 §4.1）
SERVER_HOST=... SERVER_USER=... SSH_KEY=... REMOTE_DIR=semgravio-admin INFRA_DIR=<infra 目录> \
  deploy/release.sh
```

手动等价（只复现「解包＋重建」两步；release.sh 额外补的 SSH 连通检查、infra 前置检查
与升级前备份不在其中——出问题可拆步排查，但别把手动序列当成完整发布语义）：

```bash
deploy/build-bundle.sh                 # → dist/semgravio-admin-deploy-<时间戳>.tar.gz
scp dist/semgravio-admin-deploy-*.tar.gz <user>@<host>:
ssh <user>@<host> 'cd ~/semgravio-admin && tar -xzf ~/semgravio-admin-deploy-*.tar.gz --strip-components=1 \
  && docker compose -f deploy/server.compose.yml --env-file .env.production up -d --build'
```

验收（服务器上）：

```bash
docker inspect --format='{{.State.Health.Status}}' semgravio-admin     # 等待 healthy
docker exec semgravio-admin wget -qO- http://localhost:8081/actuator/health   # {"status":"UP"...}
# webnet 内连通（admin-web 反代目标形态）——任一 webnet 容器内：
wget -qO- http://semgravio-admin:8081/actuator/health
```

### 2.5 首登与破窗账号改密（必做）

1. Flyway 负责完整迁移链（含内置 Operator 种子），JPA 不接管 schema；
   首启日志应出现 `Successfully applied N migrations` 与 `Started AdminApplication`。
2. 用内置破窗账号 `admin`（保留 ID=1，ADR-0003：只可改密、不可禁用/删除）登录
   admin-web，**首登后立即改密**（`PUT /api/admin/auth/current/password`）——初始口令经
   团队交接渠道获取（V2 种子只存 bcrypt 哈希，本档不记录明文），不得让初始口令长期留在生产。

## 3. `ADMIN_API_SECRET` 同步手册

admin 对 app-registry / aiplatform / identity / payment 的全部 BFF 签名调用走全局单 key
`admin-console`；两侧同值即签名互通，不同值则 BFF 全线 500。

- **首次抄录**：app-registry 首次部署/库重建时，启动日志打出
  `admin-console seed created, apiSecret: ...`——一次性抄录该值写入服务器
  `.env.production` 的 `ADMIN_API_SECRET`，重启 admin（`deploy/server.sh restart`）。
- **app-registry 库重建后的三步同步**（重建会重新生成随机 secret，admin 不同步即全线 500）：
  1. 翻 app-registry 启动日志 `admin-console seed created, apiSecret: ...`；日志已滚掉时，
     用 app-registry `application-local.yml` 的 `APP_REGISTRY_API_SECRET_MASTER_KEY`（Base64
     AES-256）解 `ar_api_keys` 表 `api_key='admin-console'` 行（base64(12B IV‖ct+tag)），进程内解出直写配置，勿回显；
  2. 把解出的值更新到服务器 `.env.production` 的 `ADMIN_API_SECRET`（发布不覆盖该文件，手工改）；
  3. `deploy/server.sh restart` 重启 admin 生效。
  - 也可删该行重启 app-registry 重新 seed（会再打一次日志）。
- **轮换**：口径＝固定配置值，app-registry 不重建库、不换主密钥则长期稳定；需要轮换时
  按上面三步换新值。本仓不改 app-registry 代码来适配。

## 4. 日常发布（一键换版）

### 4.1 连接参数（五个必填，脚本无任何现网默认值）

| 环境变量 | 含义 | 示例 |
|---|---|---|
| `SERVER_HOST` | 服务器地址 | `1.2.3.4` |
| `SERVER_USER` | SSH 登录用户 | `ubuntu` |
| `SSH_KEY` | 私钥路径（开发机侧） | `$HOME/ssh/<主机>.pem` |
| `REMOTE_DIR` | 远端应用目录 | `semgravio-admin`（相对 `$HOME`，绝对路径以 `/` 开头也可） |
| `INFRA_DIR` | 共享 infra 目录 | `semgravio-infra`（仅做前置健康检查） |

```bash
SERVER_HOST=... SERVER_USER=... SSH_KEY=... REMOTE_DIR=... INFRA_DIR=... deploy/release.sh
```

开关：`SKIP_BUILD=1` 复用 `dist/` 最新发布包只发布；`SKIP_BACKUP=1` 跳过部署前 pg_dump（应急，慎用）。

### 4.2 流程（任一步失败即非零退出，后续步骤不执行）

1. **前置检查（开发机）**：私钥存在、SSH 免密连通（BatchMode）。
2. **打包**：`deploy/build-bundle.sh`——默认拒绝脏工作区（源码树按 `git archive HEAD`
   导出恒 LF，与 jar 构建基线严格一致）；产物含已提交源码＋`deploy/`＋fat JAR＋`REVISION`；
   真实环境文件/私钥/证书/备份/`.scratch/` 一律不入包。`ALLOW_DIRTY=1` 可显式带脏打包（不推荐）。
3. **上传**：scp 到服务器 `$HOME`。
4. **服务器侧**（正本 `deploy/release-remote.sh`，经 SSH 灌入执行）：
   - infra 前置检查——docker/compose v2、`webnet`、`semgravio-pg`/`semgravio-redis` healthy、
     `$REMOTE_DIR/.env.production` 存在；**任何缺失即中止，不重建现有应用**；
   - 备份（§6）→ 解包（不含 `.env*`，现网 env 不被覆盖）→ 打印 REVISION →
     `docker compose up -d --build` 重建单实例容器；
   - 健康等待：容器内轮询 `/actuator/health` 最长 180s（期间 Flyway 迁移属正常）；
   - 验收：Actuator `{"status":"UP"}` 且 `/v3/api-docs` HTTP 200。
5. 完成输出容器状态表。

## 5. 服务端运维

```bash
# 连接参数同发布（SERVER_HOST/SERVER_USER/SSH_KEY）
deploy/server.sh status    # admin 容器概览（状态/镜像）
deploy/server.sh logs      # 跟日志（--tail 200）
deploy/server.sh restart   # 重启应用容器（不重建镜像、不动 infra，秒级）
deploy/server.sh dump      # pg_dump → ~/backup-admin-<时间戳>.sql.gz
deploy/server.sh smoke     # 冒烟：Actuator UP ＋ OpenAPI 可达（容器内探测，宿主无 8081）
deploy/server.sh sh        # 应用级 shell（docker exec -it 进应用容器）
deploy/server.sh ssh       # 登服务器交互 shell（应急排查）
```

- 运维入口**只面向 admin 应用容器**：不提供共享 infra（PG/Redis/nginx）或网关操作；
  infra 运维归 aiplatform 部署单元的 `deploy/infra/`。
- 日志：`docker logs -f semgravio-admin`（Flyway、BFF 下游调用错误都在这）。
- 停机：`docker compose -f deploy/server.compose.yml --env-file .env.production down`
  ——只删本应用容器，不删共享网络与卷（webnet 为 external）。

## 6. 备份与人工恢复

- **升级前自动备份**：仅当 `semgravio_admin` 库已存在（psql 可连接）才在替换容器前生成
  压缩 `pg_dump`：`~/backup-admin-<YYYY-MM-DD-HHMMSS>.sql.gz`（秒级时间戳——同分钟失败
  重跑不覆盖前一份）。首装（库不存在）不伪造旧版本备份。
- **人工恢复**（恢复是人工决策；导入前先停应用容器避免双写，并重建空库避免旧对象冲突）：

  ```bash
  docker stop semgravio-admin
  # 重建空库：删库后用 infra helper 幂等重建（cd <infra>/deploy/infra && DB_PASSWORD=<原分片> ./ensure-db-user.sh semgravio_admin）
  gunzip -c ~/backup-admin-<时间戳>.sql.gz | \
    docker exec -i semgravio-pg psql -U semgravio_admin -d semgravio_admin
  docker start semgravio-admin
  ```

- **备份≠完整回滚**：备份是升级前的数据快照，不覆盖镜像回退、配置回滚、下游域状态。
- **Flyway 限制（务必知悉）**：
  - Flyway 负责完整迁移链，JPA 不接管 schema；发布失败不会自动回滚 schema。
  - 恢复旧备份到**更新版本**的应用：旧 schema 少迁移，下次启动 Flyway 会向前补齐——
    通常可行，但迁移若含不可逆操作（删列/改型）需先核对迁移脚本再决定。
  - 恢复旧备份＋**回退旧应用包**：旧包的 Flyway 校验和与库中较新的迁移记录不匹配会
    拒绝启动——需人工清理 `flyway_schema_history` 中多出的迁移行，属破坏性操作，谨慎评估。
  - 一切以**向前修复**为优先：修复代码发新版，优于回滚。

## 7. 验收清单（分层：容器健康 ≠ BFF 全链路）

**第一层——容器健康（冒烟，无需凭据）**：`deploy/server.sh smoke`
（Actuator UP ＋ OpenAPI 200）。这只证明进程、Web 层与 PG/Redis 依赖就绪。

**第二层——BFF 全链路（Operator 登录后，四能力域只读抽检）**：经 admin-web（或
`/actuator/health` 所在服务的任一 webnet 入口）以 Operator 账号登录取得会话，逐域抽检
只读端点（均为 GET，不产生写副作用）：

| 能力域 | 端点 | 期望 |
|---|---|---|
| app-registry | `GET /api/admin/apps` | 200，应用清单分页 |
| identity | `GET /api/admin/accounts` | 200，终端账号清单分页 |
| payment | `GET /api/admin/payment/payments` | 200，支付单清单分页 |
| aiplatform | `GET /api/admin/aiplatform/orders` | 200，订单清单分页 |

任一域 500 → 先按 §3 核对 `ADMIN_API_SECRET` 同步与该域下游服务状态；401/403 → 核对
Operator 角色权限码。下游域全部健康**不是**容器启动成功的硬编码条件——分层定位。

## 8. 本地黑盒排练（改部署面后回归）

```bash
deploy/rehearsal.sh          # 仓库根；需 Docker Desktop 运行中＋干净工作区＋cartisan SNAPSHOT
KEEP=1 deploy/rehearsal.sh   # 结束后保留现场排查
```

排练从打包/发布命令的**外部行为**入手（不 mock shell 内部函数），覆盖：脚本语法与
Compose 渲染/变量契约/无宿主端口/external webnet 静态断言；脏工作区拒绝、fat JAR 可执行、
REVISION、敏感文件排除；缺参/缺钥/缺 Docker/缺 webnet、共享 PG/Redis、应用 env 的前置
失败（均不触碰现有应用）；测试专属资源（一律 `rehearsal-` 前缀：infra 容器/网络
`rehearsal-admin-*`，应用容器/镜像/项目 `rehearsal-semgravio-admin*`）上的
隔离首装、首装跳过备份、重复发布升级前备份与 `.env.production` 保留、健康超时非零退出
与现场保留；以及 webnet 内 `http://semgravio-admin:8081/actuator/health` 反代目标可达。

**口径**：排练通过＝本地黑盒验证通过；真实生产验收（真实 secret、真实共享 infra、
admin-web 联调）须在授权服务器上按本文档执行，两者不可互相替代。

## 9. 本文档明确不包含

nginx 配置、域名、证书、80/443 端口（归 admin-web）；共享 PG/Redis/nginx 的安装、升级、
停止、清理、迁移（归 aiplatform `deploy/infra/`）；旧 `semgravio` 数据库自动迁移到
`semgravio_admin`（发布不换库不迁数据）；app-registry/identity/payment/aiplatform 的部署
与代码修改；蓝绿/多实例/镜像仓库/自动回滚系统。
